好问题，这个顺序是专门排过的。

先搞懂 if / else if 怎么执行

script.js:84-109 里的快门判断，是从上往下挨个检查，碰到第一个成立的条件就执行那一支，后面的全部跳过：

if (!isOn)               → "镜头没伸出来"
else if (isEjecting)     → "还在出片"
else if (doorOpen)       → "后盖开着"
else if (!hasFilmPack)   → "没装胶片"
else if (darkSlideIn)    → 弹出黑片
else if (filmCount === 0)→ "胶片用完了"
else if (!flashReady)    → "闪光灯没充好"
else                     → 拍照

只有一个条件出问题时，顺序没影响。但现实中经常几个问题同时存在。比如相机是关着的，里面也没装胶片，这时候只有排在前面的那个条件有机会说话。

为什么"开没开机"要放第一个

因为这个顺序在模仿真机的物理顺序：

• 相机关着：镜头收在里面，快门按下去根本没反应。相机连"有没有胶片"都还没机会检查。
• 所以关机时如果提示"没装胶片"，虽然是真话，却误导用户。他会去装胶片，装完一按还是没反应，因为真正的问题是没开机。

排序原则就是：最先挡住你的问题排在最前面，也就是用户要先解决的那一步。

换了顺序会怎样（具体例子）

换法情境会发生什么
!hasFilmPack 移到 !isOn 前面关机 + 没胶片提示"没装胶片"。用户装好胶片还是拍不了，因为没开机
!flashReady 移到最前面只是没开机提示"闪光灯没充好"。关机时 flashReady 本来就是 false，所以这句话技术上不算错，但完全答非所问
filmCount === 0 移到 darkSlideIn 前面刚装好新胶片这次碰巧不影响，因为装片时 filmCount 已经是 10。可见不是每次换顺序都会出 bug，要看条件之间有没有重叠

所以顺序决定的主要是用户听到哪个解释，也就是用户体验，不只是程序能不能跑。

Event 是什么

Event（事件）就是"发生了一件事"，浏览器会把它通知给你的代码。比如：

• 用户点了一个按钮 → click 事件
• 用户在下拉框里换了选项 → change 事件
• 用户按了键盘、页面加载完成、鼠标移上去……都是事件

关键在于，这些事什么时候发生，你的代码事先不知道。用户可能 1 秒后按快门，也可能 10 分钟后才按，也可能一直不按。

跟 addEventListener 的关系

script.js:280-296 这几行就是在提前跟浏览器打招呼：

shutterBtn.addEventListener("click", pressShutter);

翻译成大白话就是："浏览器，你帮我盯着快门按钮，一旦有人点它，就去执行 pressShutter。"

• shutterBtn：盯哪个元素
• "click"：等哪种事件
• pressShutter：事件发生后要执行的函数，叫 event handler 或 callback

注意这里写的是 pressShutter，不是 pressShutter()。不带括号是"把这个函数交给浏览器，等事件来了再用"；带了括号就会立刻执行一次，那就不对了。

拨盘那两行（285、291）稍有不同，监听的是 "change"，交出去的是一个当场写的小函数：

dialSelect.addEventListener("change", () => {
  dialSetting = Number(dialSelect.value);   // 读出用户选的值，存进状态变量
  ...
  render();                                 // 刷新画面
});

这解释了我的代码为什么是这个结构

一般程序是从上往下一口气跑完。但这个网页打开以后：

1. 浏览器从上往下读一遍 script.js：定义变量、定义函数、登记监听器，最后在第 297 行调一次 render() 把初始画面画出来。
2. 然后代码就停下来等，什么也不做。
3. 用户点了按钮 → 浏览器触发事件 → 调用对应的函数 → 函数用 if / else if 检查当前状态 → 修改状态变量 → 调用 render() 更新画面。
4. 回到第 2 步继续等。

这正好对上这次作业的三个概念：

概念在代码里
State（状态）顶部那些 let isOn、filmCount……
Event（事件）用户的操作，通过 addEventListener 接进来
Control flow（控制流）事件来了以后，if / else if 根据当前状态决定怎么变

同一个"按快门"事件，在不同状态下的结果完全不同：关机时没反应，刚装片时弹出黑片，一切就绪时拍照。事件负责"什么时候"，状态 + 控制流负责"怎么反应"。

还有一种事件：时间

setTimeout（比如第 72 行的闪光灯充电）也算一种"等待以后发生"：

flashTimer = setTimeout(() => { flashReady = true; ... }, 1800);

意思是"1.8 秒后执行这段代码"。它不是用户触发的，但思路一样：登记一个函数，等某件事发生（这里是时间到了）再执行。真机的闪光灯充电、照片显影都是这么模拟的。

可以写进 Doc "Events" 那一节的话（你看完用自己的话改）：

An event is something that happens on the page, such as a click or a change, at a time my code can't predict. addEventListener lets me register a function in advance so that the browser calls it when that event happens. This is why my code isn't one top-to-bottom script. It sets up the state, connects buttons to transition functions, and then waits. Each event triggers an if / else if check on the current state, so the same shutter click can do nothing, eject the dark slide, or take a photo.
